# Review of the first independent adoption exercise

Reviewed 2026-10-20 against the complete `Independent aws-classify guide adoption…`
chat (01a155f4-65a7-7551-a333-787430489667), its commands/browser actions, final
consumer source and report. The separate `Run guide adoption test` chat dispatched
the independent chat; it was not where the app was built. Published framework
packages resolved to 0.2.3. The app lived outside this repository in a fresh
Codex-managed directory. The record shows public-guide retrieval and no framework
implementation/test inspection to discover library usage.

## Verdict

Valid independent adoption and deployed smoke test, with useful real Cognito and
CloudFront/API evidence. It is **not a completed acceptance matrix**, and is not
proof that the revised guide was fully tested. The fetched public guide was older
than this repository's revisions: its authentication YAML still used
`${aws:accountId}`, its offline instructions still suggested direct `--noAuth`,
and its navigation still said “Existing project.” The run did not preserve guide
page snapshots or a source revision. Do not describe those already corrected gaps
as regressions in the revised local guide.

The agent appropriately corrected its own extra backend `type: module` setting,
which caused the deployed CommonJS dependency failure. The guessed nonexistent
`js-freeze-dry` version and temporary TypeScript mistakes were also app-construction
errors, not demonstrated library defects. The npm/cache and local tsx incidents
have insufficient isolated reproduction to justify dependency changes.

## The reported publication defect is not established

The standalone publish failed with missing outputs while the first deployment
was still running. The recorded list of stack resources included resources still
being created; the 229-second deploy subsequently exited successfully and printed
`Published 3 files (0 removed)`. A later 42-second deploy also published successfully.
The supplied authenticated website template already defines `ContentBucket`,
`CloudFrontId` and `WebsiteUrl`. No template/output correction is warranted.

The useful correction is to await the deployment command's completion and retry
the independent publish check. The guide now says that explicitly, and tools now
report an in-progress CloudFormation status before using absent or stale outputs.
This diagnostic change has a local regression test; it has not been deployed in
another AWS run as part of this review.

## Cognito assessment

The first script provisions a pool, resource server, no-secret browser client,
domain and two users in about 85 lines; callback configuration is a separate short
script. This is straightforward fixture support, not difficult framework integration.
The initial blockers were a reserved domain prefix supplied by our test prompt,
email-username configuration incompatible with our chosen synthetic usernames,
and the normal need for an initial callback before the CloudFront URL is known.
The prompt prefix and a short provider setup-order section have been corrected.
Provider provisioning remains separate from the library, as intended.

Keep the successful provisioning sequence, but do not promote the scripts unchanged:

- Setup adopts a same-name pool from only the first listing page, without proving
  ownership, and records the manifest only after pool/resource-server/client
  creation. Failure before that write can leave unrecorded resources.
- Names are hardcoded; domain and user creation are not repeatable setup operations.
- Cleanup uses `DeleteUser` with IAM credentials and a `UserPoolId`, where the SDK
  operation requires an access token. Use `AdminDeleteUser` for explicit IAM-based
  deletion, or rely on deleting the owned pool. The observed “already absent” user
  messages therefore do not establish that the users were absent at that point.
- Cleanup treats every `InvalidParameterException` as absence. Invalid requests
  can be hidden this way. Verify absence with the appropriate describe operation
  and distinguish it from a malformed request.
- Manifest ownership is a string assertion, not verification against live pool
  name/tags. Cleanup deletes its manifest; calling it again then fails to read the
  file. There is no inventory/recovery for app-stack leftovers outside that pool.

The observed final pool absence is useful evidence of successful normal teardown;
it does not prove safe interrupted-run recovery. The existing repository AWS test
harness already has reusable CloudFormation and run-manifest cleanup patterns.

AWS documents the credential distinction in
[DeleteUser](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_DeleteUser.html)
and [AdminDeleteUser](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminDeleteUser.html).

## What to retain

Retain the one-screen app as a **partial reference smoke app** and the scenario
checklist. Do not label it the finished manual acceptance fixture or duplicate the
existing broad AWS security/race tests with it. The reference copy requires an
explicit new service name and provider scope, uses the corrected local Vite port,
and has no archived bootstrap/cleanup commands attached to it.

Archive the original report, checklist and provider script text for provenance;
this review supersedes their failure classifications. Exclude generated outputs,
passwords, credentials, node_modules and build artifacts. A maintained provider
fixture is worthwhile only after parameterization and the ownership/recovery fixes
above, with focused tests and another live setup/cleanup verification. Its creation
is not implied by preserving the unsafe first-run scripts as text.

No AWS resources were created or deleted during this review. No guide or package
was published. The original successful cleanup is assessed from the session record.
