# Proposal: Static Public Pages Alongside a SPA

Add optional hosting support for serving a SPA beneath a configurable directory, such as `/app`, alongside public HTML pages at `/` and other public URLs. Supply a reusable Serverless YAML include that reads `awsClassify.spaDirectory` from the consumer's root `package.json` and associates a CloudFront viewer-request function with the existing website distribution. It rewrites `/app` and `/app/` to `/app/index.html`, preserving query parameters, public files, assets, and API behavior; additional SPA deep-link rewrites remain an application responsibility. Update the publisher so assets beneath the configured SPA directory retain the existing long-lived immutable caching while HTML continues to require revalidation. Existing applications remain unchanged unless they opt in. Public pages use ordinary links: Sign In navigates to `/app`; the application restores its session or starts authentication, handles the provider callback there, and returns to `/` after logout. Visiting `/` always shows the public homepage. Authentication and application routing remain consumer-owned.

Complete the new-project documentation with a concrete React/TypeScript SPA creation recipe using Vite, including workspace installation, development port and API proxy configuration, build, and publication. Add an optional static-pages recipe using Minista to author complete public documents with shared components, layouts, and page-specific head content, while explaining that handwritten HTML or any other generator works equally well. Cover the shared `package.json` setting, SPA asset base and output directory, optional router base, authentication callback/logout URLs, the extra YAML include, local development, and assembling one publishable output directory without builds deleting each other's files. Use explicit public HTML URLs where necessary to avoid requiring static-page rewrites. Verify the recipe's build output, entry rewrites, API isolation, and cache headers. Vite and Minista are recipe choices, not framework dependencies; asset preloading, manifest helpers, navigation interception, dual-mode documents, and offscreen SPA initialization are outside this proposal.
